## What this repository contains

This repository regenerates the quantitative figures and the data-based
supplementary tables of the study from processed, de-identified data. Six
participants with refractory neuropathic pain are referred to throughout by the
labels **P1–P6**. Five received a chronically implanted closed-loop deep brain
stimulation system and contributed both inpatient and ambulatory data (P1–P5);
one contributed inpatient investigational data only (P6).

Each participant took part in a blinded, randomized comparison of personalized
closed-loop stimulation against sham stimulation. The closed-loop-versus-sham
contrast is therefore a within-participant condition label carried in the
figure- and table-level data files, not a fixed property of any one participant.

The figures produced here are the raw quantitative panels. The final published
figures involved hand editing by the authors in Adobe Illustrator — colors,
typography, layout, and stylistic cleanup — so panels generated by this code are
the starting point for that polishing rather than a pixel-exact match to the
printed article.

## Figures and tables generated by this repository

[`docs/FIGURE_INVENTORY.md`](docs/FIGURE_INVENTORY.md) lists every figure and
table in the article, the script that produces it, and the data that script
reads. Items with an em-dash there are published panels no script here produces
(anatomical renderings, adverse-event summaries);
Extended Data Figure 1 is one of them.

Figures are written into `figures/` as PDF; Figures 1, 5f, S5 and Extended
Data Figures 2 and 3 also write PNG and SVG copies. The Figure S11 PDFs are
600 dpi raster pages. The exceptions are Supplementary Figures S1, S2 and S3,
which are written into `python_code/decoding_figures/decoding_results/` — that
tree ships in full, so those panels can be inspected without running anything.
Every other figure script, including those for S4 and S8, writes into
`figures/`; the exploratory plots of the S8 script go to
`python_code/stability_and_closed_loop/exploratory_output/`. Figure S8 ships as
nine heatmaps, `FigureS8_<DEVICE_SIDE>.pdf`, one per implanted device side.

Tables generated by the code are written into `figures/`. The statistics CSVs
of Extended Data Figure 3 and Figure S5, the stimulation-parameter summary and
the outputs of the two processing notebooks are written back into their
`data/` folders. `data/supplementary_tables/` holds the inpatient
stimulation-parameter and biomarker tables, which are provided as data.

Running `matlab_code/MAIN_wrapper.m` regenerates every MATLAB figure end to end;
the Python figures are each produced by their own script or notebook. Both are
covered below.

## Software requirements

**MATLAB.** R2024b or newer (tested on R2024b Update 4 and R2026a Update 3). The base product plus the
Statistics and Machine Learning Toolbox (for `fitlme`, `ranksum`, `bootci`) are sufficient.

**Python.** Python 3.10 or 3.11 (the pinned SciPy does not install on 3.12), with dependencies pinned in
`python_code/requirements.txt`. Run the setup script once, with any Python 3 you
have. It finds a Python 3.10 or 3.11 on your computer, or, if there is none,
downloads Python 3.11 with [uv](https://docs.astral.sh/uv/) (into uv's own
folder, leaving your other Pythons untouched). It then creates a virtual
environment in `python_code/.venv`, installs the pinned versions, and checks
that every installed version matches `requirements.txt`:

```bash
cd python_code
python3 setup_environment.py        # Windows: py setup_environment.py
source .venv/bin/activate           # Windows: .venv\Scripts\activate
```

Or do the same by hand:

```bash
cd python_code
python3 -m venv .venv && source .venv/bin/activate      # or: conda create -n natmed python=3.10
pip install -r requirements.txt
```

## Running the MATLAB figures

No path editing is required. `MAIN_wrapper.m` locates the repository root from
its own file location, adds `matlab_code/` (including `helper/`) to the path,
and loads the shared configuration from `configure_repository.m`:

```matlab
cd matlab_code
MAIN_wrapper            % builds every MATLAB figure into ../figures/
```

To run one figure at a time, execute the setup lines the wrapper runs, then
call any figure function:

```matlab
cd matlab_code
addpath(genpath(pwd));
configuration = configure_repository(fileparts(pwd));   % repo root
plot_figureS7_acute_predicts_chronic(configuration);
```

Most figure functions take only the `configuration` struct and read their input
from `data/`; Figures 2 and 4 receive their spreadsheet from `MAIN_wrapper.m`.

| 2  | `plot_figure2_inpatient_analgesia.m` | `figure2_inpatient_analgesia.xlsx` |
| 4 (d, e) | `plot_figure4_adaptive_dbs.m` | `figure4_adaptive_dbs_performance.xlsx` |
| 5 (a–c) | `plot_figure5_double_blind_outcomes.m`, with `compute_figure5_statistics.m` for the statistics | `figure5_double_blind_outcomes/cohort_daily_percent_change.csv` (panels and statistics) |
| S7 | `plot_figureS7_acute_predicts_chronic.m` | `figureS7_acute_predicts_chronic/` (hemisphere, participant and pooled CSVs) |
| S11 | `plot_figureS11_programming_history.m` | `figureS11_programming_history/` (one CSV set per hemisphere) |

Figures 2, 5, S7 and S11 each read a CSV or spreadsheet extract from `data/`,
documented in `docs/DATA_DICTIONARY.md`. Figure S7 recomputes all of its
statistics (rank correlation, permutation p-value, bias-corrected bootstrap
interval, jackknife stability checks) inside the figure function with a
fixed random seed and prints them.

Figure 5 has two stages that read the same per-day table,
`cohort_daily_percent_change.csv`. `compute_figure5_statistics.m` fits the
linear mixed-effects model (`outcome ~ 1 + stim_group + (1 + stim_group |
patient_id)`, restricted maximum likelihood) once on the numeric rating scale and
once on each participant's index metric, and prints the residual and
Satterthwaite F tests; `plot_figure5_double_blind_outcomes.m` draws the panels.
`MAIN_wrapper.m` runs both.

`plot_pain_timecourse.m` draws main Figure 1 (P3 alone) and Extended Data
Figure 2 (P1–P5 stacked) from the same authoritative per-survey table,
`data/extended_figures_raw_pain/pain_surveys.csv`. Three behaviours
matter when running it. It is measure-selectable: the second argument names the
pain-scale column to read, the default is `painVAS`, and passing `mayoNRS`,
`unpleasantVAS` or `MPQtotal` plots that scale on its own axis;
surveys with no value in the selected column are dropped. The three panels are
derived in the plotter from the `stage` column (`pre-trial` → baseline,
`stage0` → Stage 0, everything else → chronic), so no phase column is stored in
the data. And because the pain-VAS
slider opens at 50 and records 50 again when untouched, any run of more than
four consecutive `painVAS == 50` surveys is set aside at plot time and neither
plotted nor smoothed — controlled by the `vas50_run_threshold` argument
(default 4, set 0 to disable), which never modifies the shipped CSV.

Every ambulatory survey carries the stimulation state in force when it was
taken. The moving-average line is computed over every plotted survey in a
panel, regardless of condition.

```matlab
plot_pain_timecourse(configuration);                  % Extended Data Figure 2, pain VAS
plot_pain_timecourse(configuration, "mayoNRS");       % optional NRS variant
```

`build_extended_data_table2.m` reports every pain scale each participant
provided, closed-loop versus sham, during the double-blinded crossover window.
Every count in that table is a number of participant-days; day counts are
smaller than the survey counts reported in Table S11. Figure S5 reads this CSV

```bash
cd python_code
python export_extended_data_table2_word.py
```

`plot_extended_figure3_raw_distributions.py` reads `pain_surveys.csv`, which
holds one row per survey with each pain scale in its own column. It draws six
mutually exclusive arms — baseline, open-loop optimization (unblinded),
closed-loop optimization (unblinded), closed-loop double-blind, sham double-blind
(0 mA), and washout with carryover (0 mA) — and prints the size of each at run
time. A Kruskal-Wallis test screens every arm with at least three surveys; the
closed-loop double-blind arm is then tested against baseline and against sham.

Two columns decide arm membership ahead of `condition`: `is_baseline` marks the
reference window, whose surveys are therefore left out of the washout arm, and
`is_published_closed_loop` marks the curated window reported in Extended Data
Table 2. The script raises if any survey falls in two arms or if either flag
selects no surveys for a participant.

Two versions are written. `FigureExtended3_raw_pain_distributions` shows all six
arms; `..._no_open_loop` omits open-loop optimization, the largest arm. The
statistics are identical between them.

`export_tableS11_word.py` formats the two statistics tables written by
`plot_extended_figure3_raw_distributions.py` as Table S11.1 (Kruskal-Wallis
omnibus screen) and Table S11.2 (directional post-hoc contrasts). Counts in
Table S11 are numbers of surveys. Rerun the figure script first, then:

```bash
cd python_code
python export_tableS11_word.py
```

### A note on P3 and sham

**P3 did not undergo sham testing**, so P3 has no sham condition: no sham rows
in `pain_surveys.csv`, no entry in
`sham_days.csv`, no sham
rows in `blinded_window_pain_by_day.csv`, no sham
episodes on the Figure S11 programming-history panel, no sham guesses in the
Figure 5f blinding assessment, and an em-dash in every sham column of Extended
Data Table 2, and an open circle in P3's sham slot on Extended Data Figure 3.
Every 0 mA survey of P3's recorded after therapy began is washout.

The other participants' sham sampling also differs, and the unit matters when
comparing counts. In participant-days inside the blinded window — the unit of
Extended Data Table 2 — sham contributes P1 3, P2 47, P4 4, P5 4 days, totalling
the 58 sham participant-days of the closed-loop-versus-sham model. In individual
surveys across the whole chronic record — the unit of Table S11 — the same
exposure is P1 3, P2 73, P4 9, P5 4 surveys. Day counts are the smaller of the
two because a participant may report several times per day.

P5 provided visual analogue and MPQ scores on only one of four sham days, too
few to summarise as a distribution, so those cells are withheld in Extended
Data Table 2 and the P5 sham is reported on the NRS-type measures.

## Neural data

Two neural products are shipped, both under P-only names:

- **Ambulatory biomarker extracts** in `neural_data/ambulatory_stages123/` (one
  per implanted device side; feeds Figures S8 and S4), described above.
- **Narrowband spectral features** in `neural_features/` (per-participant CSVs
  at four window lengths; the sole input to the decoding pipeline).

### Spectral features — `neural_features/`

`neural_features/` holds, for every participant and all four window lengths (1,
5, 10, 30 minutes), the narrowband spectral features that are the direct inputs
to the pain-decoding models, together with the aligned pain-score labels. Each
feature is the power in one canonical frequency band (delta, theta, alpha, beta,
low-gamma, high-gamma) on one recording contact, so a participant with *N*
contacts has *N* × 6 feature columns (column names take the form `CONTACT_band`,
e.g. `LACC1_delta`). Files live under `neural_features/P#/` as
`P#_<window>_features.csv` and `P#_<window>_labels.csv`;
`feature_file_index.csv` lists every file with its survey and feature-column
counts. The whole set is about 23 MB.

Running the decoding pipeline from these files reproduces the model results
reported in the paper: the LASSO R² (squared correlation between predicted and reported pain) and the LDA area
under the curve match the archived results exactly, and the fitted coefficients
agree to floating-point precision.

The permutation null distributions (`lasso_boots_r2s.npy`, `lda_boots_aucs.npy`
in `decoding_results/P#/`), and the p-values and significance stars that scripts
02 and 03 derive from them, come from the original analysis, which was run
without a seed. Rerunning `01_run_ml_pipeline.py` draws new permutations, so
p-values near 0.05 may randomly differ. To refit the observed models while
keeping the shipped nulls, run 01 with `--permutations 0`. LDA models with fewer
than 3 surveys in the low- or high-pain group are not fitted and are reported as
N/A (`MIN_SURVEYS_PER_CLASS` in `01_run_ml_pipeline.py`): leave-one-out training
then holds a single survey of one group, the covariance is singular, and the AUC
would depend on rounding error. This applies to 5 P5 models.

**Why survey counts differ across window lengths.** A survey is retained for a
given window only if it is preceded by enough continuous, artifact-free
recording of that length, so longer windows are available for fewer surveys.
Surveys spaced closer together than the window length are dropped, and windows
containing stimulation-testing periods or other flagged artifacts are excluded
during featurization.

## De-identification

Participants are referred to as P1–P6 throughout, and neural recordings are
stored as numeric arrays with contact labels only.

**Dates are blinded by a fixed per-participant shift** — one offset per
participant, a whole number of weeks, applied to every date and timestamp in
every shipped file. This is the standard HIPAA Safe-Harbor approach, as used by
the MIMIC critical-care database. Whole-week offsets preserve every
within-participant interval, ordering, weekday and time-of-day, so all analyses
and figures are numerically identical to the originals. The offset differs
between participants, so cross-participant date arithmetic reveals nothing, and
it is applied uniformly, so no file pairs a shifted copy of an event with an
unshifted one from which the offset could be recovered.

**Residual re-identification risk.** No de-identification is absolute. This
deposit retains implant target anatomy per hemisphere, each participant's
symptom trajectory, and a small cohort size — features intrinsic to the
scientific content, since they are what the figures report. Anyone reusing these
data must not attempt to re-identify participants.

This deposit is organized to support the NIH HEAL Initiative data-sharing
